# 统一灰盒检测规范

## 1. 文档目标

本规范用于约束以下两个已部署项目在每次版本部署后的标准化灰盒检测流程：

- `G:\AIproject\longxia_keli\hermes-web-ui`
- `G:\AIproject\longxia_keli\quantclaw_singup\quanthermes`

规范目标如下：

- 建立统一、可重复执行、可审计的灰盒检测标准
- 在已知部署结构、系统职责、接口边界和运行依赖基础上开展验证
- 覆盖通用检测维度和项目专属场景，减少遗漏
- 为每次版本上线后的放行决策提供一致依据
- 将问题发现、记录、整改、复测、关闭纳入统一闭环

本规范适用于以下场景：

- 生产环境首次部署后的验收检测
- 生产环境版本升级后的回归检测
- 热修复版本部署后的重点复核
- 现场设备重装、迁移、回滚后的补充检测

## 2. 灰盒检测定义与边界

本文定义的灰盒检测，是指在掌握项目基本架构、核心接口、部署方式、关键依赖、配置模型和主要业务链路的前提下，对系统部署结果与运行结果进行结构化验证。

灰盒检测边界如下：

- 允许参考代码结构、接口契约、部署脚本、配置文件和运行文档
- 允许调用健康检查、状态接口、业务接口、日志、浏览器控制台和系统服务状态
- 不直接修改生产数据、核心配置或源代码
- 不执行破坏性压测、恶意渗透或超出授权范围的安全攻击
- 不替代单元测试、集成测试、白盒代码审查和正式渗透测试

## 3. 项目基线调研摘要

### 3.1 `hermes-web-ui` 基线摘要

`hermes-web-ui` 是一个 TypeScript Monorepo，核心由以下部分组成：

- Web 客户端：Vue 3、TypeScript、Vite、Pinia、Vue Router、vue-i18n、Naive UI
- 服务端：Koa 2、Socket.IO、SQLite、本地文件与任务编排能力
- 桌面端：Electron 封装与本地运行时引导
- 部署方式：源码部署、Docker 部署、设备侧 systemd 部署、桌面端打包分发

核心业务模块包括：

- 登录与鉴权
- 单聊与会话管理
- 群聊与多 Agent 协作
- Profiles、Models、Providers、Skills、Plugins、Memory、Logs、Settings 等控制面能力
- 文件上传下载与本地工作区访问
- 更新控制与设备部署编排

关键交互特点如下：

- 管理类能力以 REST API 为主
- 实时消息、流式输出、群聊协作、终端能力以 Socket.IO 为主
- 部分部署能力依赖 systemd、环境变量文件、更新脚本和设备目录结构

### 3.2 `quanthermes` 基线摘要

`quanthermes` 是部署在设备侧的新板本地服务项目，核心由以下部分组成：

- 本地 HTTP 配网页面
- 本地 API 服务
- WiFi/AP 模式控制
- 设备注册与心跳上报
- kiosk 配网页与业务页切换
- OTA 更新检查与触发钩子

核心接口包括：

- `GET /api/health`
- `GET /api/status`
- `GET /api/wifi/scan`
- `POST /api/config`
- `POST /api/reset`
- `POST /api/phone`
- `POST /api/update`
- `GET /api/update/status`

关键运行依赖如下：

- Linux 设备环境
- systemd
- NetworkManager、`nmcli`、`iw`
- `dnsmasq`
- Chromium kiosk
- 本地配置文件与状态文件目录

关键业务链路如下：

- 设备启动后根据已保存配置决定进入 AP 还是尝试连接 WiFi
- 配网成功后保存配置并触发设备注册和心跳上报
- 状态接口驱动前端显示与 kiosk 自动切屏
- 更新接口与心跳回包共同参与 OTA 流程

## 4. 统一灰盒检测范围标准

统一灰盒检测范围必须覆盖以下五大核心维度，任何版本部署后均不得裁剪：

### 4.1 核心业务链路合规性

目标是确认核心业务流程从入口到结果均符合预期，没有出现逻辑断链、状态漂移、关键字段缺失或错误放行。

必须覆盖：

- 主业务入口可访问
- 关键业务提交可成功完成
- 关键状态在前端、接口、日志和系统侧表现一致
- 核心成功路径、失败路径、回退路径均可解释

### 4.2 接口前后端交互正确性

目标是确认前端请求、后端响应、实时事件、状态同步和错误反馈一致且可追踪。

必须覆盖：

- 请求参数与接口契约一致
- 状态码、错误码、错误文案符合预期
- 前端展示与接口返回一致
- 必要时序下不会出现脏数据、重复提交、消息乱序或状态卡死

### 4.3 部署后的配置完整性

目标是确认部署后程序、依赖、配置、服务注册和目录结构完整可用。

必须覆盖：

- 服务进程成功启动
- 配置文件完整且值合法
- 环境变量、目录权限、端口绑定正确
- 依赖服务与外部资源连接正常
- 更新、回滚、重启后关键配置不丢失

### 4.4 权限管控有效性

目标是确认认证、授权、敏感配置和高风险操作受控，没有出现越权访问、未鉴权入口或敏感信息泄露。

必须覆盖：

- 鉴权接口与受保护接口的边界正确
- 高风险操作需要明确权限或前置条件
- 敏感字段不在日志、前端响应或错误栈中裸露
- 无效 token、失效会话、越权参数能够被拒绝

### 4.5 基础性能稳定性

目标是确认系统在灰盒检测范围内具备基本可用的吞吐、响应、恢复和稳定能力。

必须覆盖：

- 健康检查持续可用
- 核心接口响应时间在阈值内
- 实时链路和状态轮询无明显堆积
- 重复执行关键操作后系统不出现显著退化
- 服务重启后能够恢复到可用状态

## 5. 通用检测场景

以下为两个项目共同适用的通用检测场景：

- 服务部署完成后健康检查接口返回成功
- 主服务进程、依赖进程和端口监听符合部署预期
- 核心配置文件存在、内容完整、关键值未缺失
- 关键 API 在正常参数、异常参数、缺失参数下响应正确
- 前端页面与接口返回的数据一致
- 鉴权失败、会话过期、权限不足时返回正确错误
- 日志中无大面积报错、无未处理异常、无敏感信息直出
- 版本号、构建时间、环境配置与实际部署包一致
- 服务重启、网络短暂波动、浏览器刷新后关键业务可恢复

## 6. 项目专属检测场景

### 6.1 `hermes-web-ui` 专属检测场景

除通用场景外，必须额外检测以下内容：

- 登录链路、token 签发与续用
- `Authorization` 头与活动 profile 头是否正确传递
- 单聊消息提交、流式返回、终止、重试、恢复
- 群聊消息广播、成员身份、实时状态和错误提示
- 文件上传、文件列表刷新、引用消息或附件后的联动
- REST 与 Socket.IO 在同一业务流中的状态一致性
- 设置、Providers、Models、Skills、Memory 等控制面配置保存后是否即时生效
- 更新控制接口、更新请求落盘、更新前校验与失败回退行为
- 设备部署、Docker 部署、桌面端部署中至少覆盖当前发布实际使用的部署形态

### 6.2 `quanthermes` 专属检测场景

除通用场景外，必须额外检测以下内容：

- 配网页面入口可访问，常见 captive portal 路径可回到首页
- `GET /api/status` 的模式、阶段、网络摘要、显示模式等字段完整且含义一致
- `GET /api/wifi/scan` 能返回有效列表，异常时有可理解错误
- `POST /api/config` 提交后，配置落盘、切网动作、回退逻辑和状态更新符合预期
- `POST /api/reset` 后，清理保存配置并回 AP 模式成功
- 设备注册和心跳上报按预期触发，关键字段完整
- kiosk 根据状态切换到配网页或业务页，不出现错误卡屏
- `systemd` 服务、NetworkManager、`dnsmasq`、浏览器和端口占用状态符合部署预期
- 更新接口与状态接口在无更新、有更新、更新失败三种状态下表现正确

## 7. 检测前置条件

开始灰盒检测前，必须同时满足以下前置条件：

- 两个项目均已完成生产环境部署或与生产等价的预发布部署
- 当前部署版本号、构建包来源、部署时间、执行人信息明确
- 所有必需依赖服务正常运行
- 关联数据库、文件目录、系统服务、网络依赖已完成启动检查
- 检测账号、设备、浏览器、终端、网络环境已准备完毕
- 检测工具已完成环境适配并可正常采集数据
- 本次检测目标版本的变更范围已提前识别

如任一前置条件不满足，本轮灰盒检测不得标记为正式有效结果。

## 8. 检测执行流程规范

统一执行顺序固定如下，不得随意调整：

### 8.1 第一阶段：后端接口灰盒检测

先对所有核心接口进行接口级验证，确认接口自身行为稳定，再进入联调。

本阶段重点：

- 接口连通性
- 参数校验
- 状态码和错误码
- 鉴权与权限
- 幂等性与重复调用
- 配置、状态、日志的一致性

### 8.2 第二阶段：前后端联调链路检测

在接口验证通过后，再验证页面、前端状态、后端响应、实时事件和日志之间的一致性。

本阶段重点：

- 表单提交流程
- 页面数据回显
- 实时流、轮询、消息同步
- 前端错误提示
- 状态变化时序

### 8.3 第三阶段：端到端业务流检测

最后从用户视角串联完整业务流，确认系统作为整体可用。

本阶段重点：

- 关键正向业务流
- 关键异常业务流
- 回退或恢复业务流
- 跨模块协同链路

### 8.4 问题记录与闭环要求

检测执行期间发现任何问题时，必须立即记录以下信息：

- 问题标题
- 所属项目
- 所属版本
- 检测阶段
- 场景描述
- 复现步骤
- 实际结果
- 预期结果
- 影响范围
- 严重级别
- 附件证据
- 当前状态
- 责任人

问题流转必须遵循以下闭环要求：

- 当轮检测发现的问题必须全部登记，不允许口头带过
- 致命和高危问题必须在放行前修复并完成复测
- 中危问题若不立即修复，必须给出明确风险说明、缓解措施和计划版本
- 低危问题可进入后续迭代，但必须保留记录与跟踪编号

## 9. 检测指标与判定标准

### 9.1 单项检测项 Pass/Fail 规则

每一个检测项必须按以下规则判定：

- Pass：执行结果与预期完全一致，证据完整，未发现残留风险
- Fail：执行结果与预期不一致，或虽然功能可用但存在明确缺陷、越权、配置缺失、状态异常、性能超阈值等问题
- Blocked：受外部条件限制无法执行，例如依赖服务异常、测试数据缺失、现场设备不可用；Blocked 不得计入 Pass

### 9.2 整体通过率阈值

整体放行必须同时满足以下条件：

- 核心业务链路检测项通过率达到 `100%`
- 全量已执行检测项通过率不低于 `95%`
- 所有致命问题为 `0`
- 所有高危问题为 `0`
- Blocked 项必须有书面原因、影响评估和补测计划

### 9.3 高风险问题清零要求

出现以下任一情况，当前版本不得放行：

- 任一核心链路存在致命问题
- 任一高危权限问题未解决
- 任一关键配置缺失导致重启后不可恢复
- 任一更新或部署链路存在高概率失效风险
- 任一设备侧网络切换导致系统长期不可达

## 10. 问题分级标准

### 10.1 致命

满足以下任一条件即归类为致命：

- 系统无法启动或核心服务不可用
- 核心业务主链路完全中断
- 大范围数据错误或不可恢复
- 高风险操作导致服务不可达或现场设备失联
- 存在严重越权或敏感信息泄露，可直接造成业务事故

### 10.2 高危

满足以下任一条件即归类为高危：

- 核心业务链路可进入但结果错误
- 关键接口大概率失败或状态不一致
- 关键配置缺失，重启、升级或切换后会触发明显故障
- 身份校验、权限控制、更新控制存在明显绕过风险
- 性能显著恶化，已影响正常使用

### 10.3 中危

满足以下任一条件即归类为中危：

- 非核心功能异常但影响用户体验或运维效率
- 错误提示不清、部分状态不一致、偶发失败可重试恢复
- 非核心配置项缺失，但暂不阻塞主流程
- 监控、日志、可观测性不足导致排障成本明显升高

### 10.4 低危

满足以下任一条件即归类为低危：

- 文案、样式、提示轻微问题
- 个别边界场景可优化但不影响主流程
- 不影响放行的文档、日志、展示类问题

## 11. 检测工具选型与使用规范

### 11.1 接口测试工具

推荐工具：

- Postman 或 Apifox：用于 REST API、鉴权、参数化回归、环境变量管理
- `curl`：用于设备侧快速验证、脚本化回归和现场应急复核

使用规范：

- 每个接口必须明确请求样例、鉴权方式、预期响应和异常响应
- 环境变量中不得明文记录生产敏感密钥
- 请求与响应样本必须保留版本号和时间戳

### 11.2 前端监控与浏览器工具

推荐工具：

- Chrome DevTools：用于 Network、Console、Application、Performance 基础分析
- 浏览器 HAR 导出：用于保留接口联调证据

使用规范：

- 关键操作至少保留一次完整网络抓包证据
- 控制台报错必须与问题单绑定，不得仅截图不说明
- 本地缓存、token、session 存储需纳入鉴权类检查

### 11.3 链路追踪与日志工具

推荐工具：

- 浏览器控制台与 Network 面板
- Koa 服务日志、systemd 日志、设备侧 `journalctl`
- 应用状态接口与健康检查接口

使用规范：

- 日志采集需包含时间、场景、请求标识或设备标识
- 若无统一 trace id，则至少保证同一问题记录中包含时间窗口与关键接口路径
- 日志证据必须能支持问题复现或根因分析

### 11.4 性能与稳定性验证工具

推荐工具：

- Chrome Performance 基础录制
- `ab`、`hey` 或等价轻量 HTTP 压测工具，仅用于低强度基础验证
- `top`、`free`、`ss`、`systemctl`、`journalctl` 等系统命令

使用规范：

- 仅执行基础稳定性验证，不在生产执行高强度压测
- 样本数、并发数、持续时间必须提前记录
- 发现性能异常时需同步记录 CPU、内存、连接数和日志表现

## 12. 数据采集标准

每一轮灰盒检测至少应采集以下证据：

- 部署版本信息
- 检测环境信息
- 接口请求和响应样本
- 前端页面截图或录屏
- 浏览器网络抓包或 HAR
- 服务端日志片段
- 设备侧系统服务状态
- 问题单与复测记录

所有证据必须满足以下要求：

- 可追溯到具体版本
- 可追溯到具体执行时间
- 可追溯到具体检测人
- 可追溯到具体项目和检测项

## 13. 角色分工与发布准入

建议采用以下角色分工：

- 发布负责人：确认版本、环境、窗口期和放行结论
- 灰盒检测执行人：执行检查、记录证据、提交问题
- 开发负责人：分析根因、修复问题、提供复测说明
- 运维或设备负责人：保障部署环境、服务依赖和系统权限正确

版本放行必须满足以下准入要求：

- 已完成本规范要求的全部必测项
- 已生成本轮灰盒检测报告
- 致命和高危问题全部清零
- 中低危遗留项已被确认并纳入后续计划
- 发布负责人明确签字或书面确认

## 14. 版本执行频率要求

以下情形必须执行完整灰盒检测：

- 主版本发布
- 涉及登录、权限、更新、设备网络、注册上报、实时消息的功能变更
- 涉及 systemd、环境变量、部署目录、服务端口变更

以下情形可执行裁剪版灰盒检测，但不得跳过核心链路：

- 仅文案或样式修复
- 仅非核心管理页局部调整
- 已确认不影响部署与权限边界的小范围修复
