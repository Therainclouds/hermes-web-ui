# 耀丰地产案件 · 无人值守长跑任务模板（8-10 小时）

> 用途：在「许-测试1」房间（mst1i96yngn9nj）发起一场跨夜自由讨论，
> 让 5 个 agent 自动完成耀丰地产卷宗的完整办案分析并产出交付文件。
> 基于实测：单轮 8-10 分钟、第 5 轮自动归档、收敛需连续 2 轮裁判判定。

---

## 一、发起参数（UI「发起自由讨论」填写）

| 参数 | 值 | 说明 |
|---|---|---|
| 最大轮数 maxRounds | **40** | 40 轮 × ~10 分钟 ≈ 6.7 小时，留余量防单轮变慢 |
| 最小轮数 minRounds | **15** | 前 15 轮禁止收敛，强制深度探索 |
| 消息上限 maxMessages | **600** | 实质发言每轮约 6 条，40 轮 ≈ 240 条，3 倍余量 |
| 参与 Agent | 全部 5 个 | default / guanzhong / jiran / wenxin / zimo |
| 汇报 Agent | default（以沫） | 综合汇报由文书专员负责 |
| 裁判 | 房间默认 deepseek-v4-pro | 无需改动 |

## 二、任务文案（复制到「讨论目标」输入框）

```
【任务目标】基于设备上的耀丰地产建设工程施工合同纠纷卷宗，产出一套完整的办案分析成果：
1. 卷宗盘点与证据索引；2. 三大争议焦点（违约金/工程款/工期）的实质分析结论；
3. 综合质证方案；4. 最终交付报告。全部完成才算任务结束。

【材料位置】卷宗根目录：/home/hermesui/yaofeng/耀丰地产/
（7 个顶层目录、203 个文件，含 94 份 PDF，存在 iFile 同步冲突产生的重复目录，
盘点时需去重识别。）

【阶段划分】按以下 4 个阶段依次推进，每阶段内部多轮深化，不要跳阶段：
- 阶段一（约第 1-10 轮）：全量盘点卷宗、识别重复目录、建立证据索引（含每份
  关键证据的名称、路径、证明目的、可读性状态：文本层/需OCR/图片）
- 阶段二（约第 11-22 轮）：围绕三大争议焦点逐一读取关键证据并分析——
  违约金（条款依据、计算基数、起算时点）、工程款（已付/未付金额、利息计算表
  口径复核）、工期（延误责任认定、索赔依据）；每个结论必须注明所依据的证据
  文件路径
- 阶段三（约第 23-32 轮）：基于前两阶段结论，产出综合质证方案——按争议焦点
  列出我方/对方证据的质证要点、证明力评价、庭审应对建议
- 阶段四（约第 33-40 轮）：汇总全部成果，产出最终交付报告（含结论、依据、
  风险提示、建议下一步动作）

【每轮要求】每轮结束前，发言 agent 必须：
1. 实际调用工具读取/核验材料（不要凭记忆复述）；扫描 PDF 按需 OCR；
2. 输出本轮新增的实质结论或进展，避免复述他人已说内容；
3. 阶段一至三每阶段完成时，立即把该阶段成果保存为 Markdown 文件到交付目录
   （绝对路径：/home/hermesui/.hermes-web-ui/group-chat/default/mst1i96yngn9nj/交付/），
   文件名带阶段号，如「耀丰案-阶段1-卷宗盘点与证据索引.md」。

【完成标准】当且仅当同时满足以下条件才算完成：
1. 4 个阶段的 Markdown 文件都已落盘到交付目录；
2. 三大争议焦点均给出基于具体证据文件路径的结论；
3. 综合质证方案覆盖全部争议焦点；
4. 最终交付报告完整、自洽、可直接使用。
（未满足上述全部条件前，即使意见一致也不得结束。）

【禁止事项】
- 不要反问用户、不要等待用户决策、不要请求用户介入；
- 材料无法读取时，标注"需人工核实"而不是编造内容；
- 不要输出空回复；
- 不要修改交付目录之外的文件。
```

## 三、发起方式

**方式 A（推荐）**：UI 房间设置 → 发起自由讨论 → 粘贴上面的任务文案 →
按第一节参数表填写 → 开始。

**方式 B（命令）**：
```
/讨论 耀丰地产卷宗办案分析：卷宗盘点→三大争议焦点分析→质证方案→最终交付报告，全程自动完成并落盘交付目录 @全体
```
（命令方式用默认参数，需在发起前到设置里把最大轮数调到 40。）

## 四、发起前 5 分钟冒烟测试（务必先做）

1. 先用**短任务**（maxRounds=2）验证：agent 能读取卷宗路径、工具（文件列表/
   pdftotext/OCR）正常、交付目录可写。
2. 确认冒烟测试产出 1-2 个文件后，**停止**该短讨论，再按完整模板发起长跑。
3. 发起后观察前 2 轮是否正常推进（状态 running、轮次递增、消息在增加），
   确认无误后即可离开。

## 五、第二天早晨检查清单

1. **交付目录**：
   `ssh root@10.0.0.2 "ls -la '/home/hermesui/.hermes-web-ui/group-chat/default/mst1i96yngn9nj/交付/'"`
   应看到 4 个阶段文件 + 最终报告 + 讨论总结.docx。
2. **讨论状态**：GET `/api/hermes/group-chat/rooms/mst1i96yngn9nj/discussion`
   - `status: converged` = 裁判判定完成（最佳）
   - `status: max_rounds` = 跑满 40 轮（正常兜底）
   - `status: stopped/failed` = 异常，查日志
3. **服务日志**：`journalctl -u hermes-web-ui --since "12 hours ago" | grep -iE "archive|Discussion|error"`
   重点看是否有归档失败、agent 发言超时。
4. **设备健康**：`free -m` 可用内存应 ≥ 1.5GB（zram 兜底）；若发现内存被吃爆
   且讨论未结束，用 `systemctl restart hermes-web-ui` 重启（进行中讨论会标记 failed，
   但已落盘的阶段文件不受影响——这就是每阶段落盘的意义）。

## 六、预期时间线

| 阶段 | 轮次 | 预计耗时 | 里程碑 |
|---|---|---|---|
| 阶段一 盘点 | 1-10 | ~1.5-2h | 证据索引.md 落盘 |
| 阶段二 焦点分析 | 11-22 | ~2-3h | 三大焦点结论落盘（第 15 轮后允许收敛） |
| 阶段三 质证方案 | 23-32 | ~1.5-2h | 质证方案落盘 |
| 阶段四 汇总交付 | 33-40 | ~1.5-2h | 最终报告落盘 + 讨论总结.docx |

若裁判在阶段二后连续 2 轮判定 converged（minRounds=15 已过），讨论可能提前结束——
这是正常收敛，检查交付文件是否齐全即可。

## 七、已知注意事项

- 卷宗存在 `0-客户提供基础资料` 与 `(1)` 副本等重复目录，agent 必须去重，
  裁判也会据此判断是否在"原地打转"。
- 部分 PDF 无文本层（之前实测 7 字符/19 字符的文本层），需要 OCR，单轮可能
  因此变慢到 12-15 分钟——maxRounds=40 已预留余量。
- 若中途设备重启/断电，进行中的讨论会标记 failed，但已落盘的阶段文件保留，
  第二天可基于已有成果重新发起（阶段文件可作为新讨论的附件）。
