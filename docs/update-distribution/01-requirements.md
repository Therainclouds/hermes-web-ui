# 01. 需求与约束

- 状态：draft
- 负责人：Cloud
- 最后更新时间：2026-06-07
- 依赖：`docs/deploy-update-runbook.md`、`docs/deploy-source-armbian.md`

## 背景

当前设备端更新链路已经具备版本检测 + 页面触发更新的基础能力：

- 版本检测通过 `npm registry` 实现。
- 页面更新通过 `source-deploy` 实现。
- 更新脚本会下载 GitHub tag archive，再调用 `deploy-source-armbian.sh` 完成重建和重启。

现有问题是：GitHub tag archive 在设备侧下载速度慢、稳定性差，而且更新检测源与实际下载源分裂，后续难以稳定支持校验与回滚。

## 目标

本方案目标如下：

- 首次部署与后续页面更新都稳定可用。
- 更新包从自有下载源获取，不再依赖 GitHub archive 作为主链路。
- 保持当前部署模式：源码部署 / 一键部署脚本 / `systemd`。
- 更新流程支持校验、失败自动回退，并为未来手动回滚预留结构。
- 用户可以像消费电子设备一样自己选择是否更新。
- 工作结果必须透明、可追溯、可审阅。

## 非目标

以下内容不在本轮设计范围内：

- 替换 Electron 桌面端自动更新协议。
- 替换 Docker / 容器更新模式。
- 建设灰度控制台、批量设备编排系统。
- 开放用户自定义下载源、跳过校验、任意安装历史版本。
- 将整个主服务改为 `root` 常驻运行。

## 已确认约束

- 设备运行模式仍以 Linux + `systemd` 为主。
- 设备更新脚本仍以 Bash 执行。
- 主服务应常驻非 `root` 用户，更新安装阶段短时提权。
- 第一阶段必须兼容现有 `source-deploy` 链路与环境变量。
- 当前仓库的 controller 应保持薄层，复杂逻辑应下沉到 `services` 或脚本模块。

## 产品约束

- 登录用户应可触发升级到当前官方稳定版。
- 高风险动作保持受限，不作为普通用户能力开放：
  - 切换更新源
  - 切换通道
  - 安装指定旧版本
  - 手动回滚
  - 关闭摘要校验

## 术语

- `device-package`：设备真正下载和安装的更新包。
- `manifest`：描述最新版本、下载地址、摘要、兼容性和回滚元数据的清单文件。
- `source-deploy`：当前源码部署更新模式。
- `privileged installer`：带受控高权限的安装器脚本，只负责安装和回退，不承担 Web UI 常驻服务职责。
- `last-known-good`：最后一次验证通过、可正常启动的版本快照。

## 成功标准

- 设备可以从自有下载源稳定获取更新包。
- 安装前完成清单与 `sha256` 校验。
- 安装失败后可以自动恢复到上一个可运行版本。
- 文档能指导后续实现、验收和运维排障。
