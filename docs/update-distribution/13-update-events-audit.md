# 13. 近 3 次更新事件审计

- 状态：active
- 负责人：Cloud
- 最后更新时间：2026-07-02
- 适用范围：近期更新事件复盘、问题清单、责任归属、规则回写

## 审计方法

- 按事件批次而不是单纯按版本号整理。
- 每个事件记录：触发场景、问题类型、影响范围、根因、责任主体、修复动作、预防规则。

## 事件一：在线更新错误进入旧 npm/CLI 分支

- 触发场景：页面检测到新版本后点击更新。
- 问题类型：流程分流错误、运行时职责混杂。
- 影响范围：`device-package` 更新任务未进入受控 runner，状态文件、runner request、日志缺失。
- 直接表现：
  - 没有 `update-runner-request.json`
  - 没有 `update-task-state.json`
  - 没有新的 `device-package-*.log`
  - 设备侧仍走旧的 npm/CLI restart 逻辑
- 根因：
  - 服务端更新入口没有按策略完整分流。
  - 历史 npm 更新链路与新的 managed runner 链路共存但边界未收紧。
- 责任主体：
  - 开发团队主责
  - 发布负责人次责
- 预防规则：
  - controller 必须按 `strategy` 分流到受控 runner。
  - 更新失败不能只看页面提示，必须检查任务状态文件和 runner 日志。

## 事件二：固定版本引导与端口漂移

- 触发场景：旧设备手工引导到指定版本。
- 问题类型：现场 SOP 依赖人工经验、环境继承不稳定。
- 影响范围：设备端口从现场原值漂移到默认值，典型为 `6060 -> 8648`。
- 直接表现：
  - 更新后页面无法按原端口访问
  - `/etc/default/hermes-web-ui` 中 `PORT` 被错误回退
- 根因：
  - 使用 `stable/latest.json` 替代固定版本 manifest。
  - 手工安装前没有显式继承设备原环境变量。
  - 安装器默认值在现场场景中成为了隐式覆盖源。
- 责任主体：
  - 运维团队与开发团队共同负责
- 预防规则：
  - 固定版本引导必须使用目标版本 `manifest.json`。
  - 手工引导前必须显式保留 `PORT`、`BIND_HOST`、`DEPLOY_DIR` 和状态目录。

## 事件三：设备包内容不完整与更新超时

- 触发场景：近期版本发布与设备侧升级。
- 问题类型：发布物完整性校验不足、更新链路时序脆弱。
- 影响范围：
  - 设备包缺少运行时脚本
  - 更新流程出现超时
  - 版本发布后需要再次补丁修复
- 根因：
  - 发布工作流之前对最终交付物真实可用性的校验不够强。
  - 更新链路存在多阶段耦合，任何脚本遗漏都可能在设备侧放大。
- 责任主体：
  - 发布负责人主责
  - 开发团队协同
- 预防规则：
  - 发布 workflow 必须验证最终资产真实可下载、摘要一致、关键运行时文件齐全。
  - 更新脚本与发布契约需要共享字段语义，不能各自演化。

## 共性根因分类

- 产品边界模糊：把 Web UI 更新、Agent 升级、宿主机治理混成一个“更新系统”。
- 技术框架适配不合理：页面内更新承担了不应承担的 root/runtime 职责。
- 发布契约分散：workflow、manifest、controller、installer 之间没有完全共享单一事实源。
- 现场执行过度依赖经验：靠 SOP 和口头提醒弥补脚本和规则缺口。

## 结论

- 近期问题并非孤立 bug，而是边界与职责未收敛导致的系统性问题。
- 本目录的规则、边界文档和脚本显式开关，是当前阶段避免同类问题重复发生的最低落地方案。
