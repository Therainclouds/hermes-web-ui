## 本轮已确认项

1. 第一阶段先做“边界保护 + 模块收敛”，暂不直接进入 `device-package` 执行闭环。
2. 第一阶段目录策略采用分级治理，而不是一刀切阻断：
   - 低风险：正常更新
   - 中风险：告警但允许更新
   - 高风险：阻止更新
3. `Web UI` 默认数据目录继续保持在用户家目录下，不改变当前默认策略。
4. 第一阶段重点是保护真实数据路径，避免更新覆盖数据，而不是强制统一现场目录结构。
5. 当前 `HERMES_HOME_DIR` 历史布局需要兼容处理，不能因为规则过死引发新的权限纠纷。
6. 第一阶段目录保护需要同时覆盖 `source-deploy` 和 `npm-package` 两条服务端更新路径。

## 当前待确认项

1. `install-device-package.sh` 是以 `sudoers` 调用脚本形式实现，还是单独 root helper 形式实现。
2. 设备包第一阶段是否只包含 `dist + scripts`，还是保留更多源码级内容以兼容现有 update-only 构建逻辑。
3. 需要保留多少个 last-known-good 备份，磁盘预算是多少。

## 已关闭的问题

- “第一阶段是否要把所有位于 `DEPLOY_DIR` 内的数据目录直接判为危险并阻止更新”
  - 结论：否。当前规则改为按真实数据路径和风险分级处理，并兼容现有 `HERMES_HOME_DIR` 历史布局。
- “第一阶段是否要强制迁移 `HERMES_HOME_DIR`”
  - 结论：否。第一阶段不自动迁移，也不强制统一现场目录结构，先保证更新不覆盖数据。
- “第一阶段版本发现入口是否继续保留 `latest.json`”
  - 结论：是。当前继续使用 `latest.json` 作为稳定入口，优先提升发布闭环稳定性，不把下载提速纳入本轮范围。
- “发布工作流是否独立拆分”
  - 结论：是。新增独立 `device-package-release.yml`，不混入现有 `npm-publish.yml`。
- “第一阶段下载承载是否继续使用 GitHub”
  - 结论：是。设备包、`sha256` 和版本 `manifest.json` 由 GitHub Release 承载，`latest.json` 和版本元数据由 `release-manifests` 分支承载。
